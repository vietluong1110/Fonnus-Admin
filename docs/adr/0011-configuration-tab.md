# ADR 0011: The Configuration tab — a form generated from the pipeline's contract file, one appended `runtime_config` row per save, reviewed before it lands

**Status:** accepted 2026-09-19 · **Date:** 2026-09-19 · Stands on ADR 0007 (the write posture: the
insert of contract §7 as `console_editor`, signed with the account Caddy authenticated),
ADR 0003 (design system by copy), ADR 0006 (the URL is the whole input), ADR 0009 (the
`runtime.version` reader), and on the pipeline's ADR 0020 (the runtime config layer),
ADR 0021 (the document schema shared by copy, the drift gate, the editable texts, disclosure
advice) and ADR 0028 (every vendor offered, the box refuses per call). Library and bundler
facts verified 2026-09-19 — §Verified facts. Implements PLAN row A9 under the six rules of
`docs/redesign.md` §4.2.

## Decision

The console gains one screen, **Configuration** at `/configuration`, the sidebar item after
Calls. It reads a tenant's `runtime_config` rows and writes exactly one thing: a new row.
The rules this console adds to what the contract, the pipeline's ADRs and `docs/redesign.md`
already fix:

**1. The contract files are copied byte for byte and read through one bundler alias.**
`../Fonnus/app/src/config/runtime-document.ts` and `../Fonnus/app/src/domain/speakable.ts`
land as `src/contract/config/runtime-document.ts` and `src/contract/domain/speakable.ts`,
the same relative layout so the one relative import between them (`'../domain/speakable.js'`)
is unchanged. No header line, no re-export, no edit of any kind: the bytes are what the
contract's two `contract-hash:` lines in `../Fonnus/docs/read-contract.md` §7 pin, and a
console-side change would fail the drift test the moment it landed. The rest of the console
reaches the file through `@/contract/config/runtime-document` only; nothing imports the
speakable copy directly.

Turbopack does **not** resolve a `.js` specifier to a `.ts` file under this repo's
`moduleResolution: bundler` (it gates that substitution on `nodenext` — §Verified facts, by
observation), while `tsc` and vitest both do. So `next.config.ts` gains one line under
`turbopack.resolveAlias`: the request string `'../domain/speakable.js'` maps to
`./src/contract/domain/speakable.ts`. The key is the exact specifier the copy uses; nothing
else in this repo has a `domain/` directory, so the alias can match nothing but the copy.
*Enforcers:* `pnpm build` (without the alias the build fails with `Module not found`, which is
how it was found); the drift test's import check (rule 2c) pins that the copy's only
relative import is that exact string, so the alias and the specifier cannot drift apart
silently.

**2. One drift test holds the copies to the contract** — `src/contract/contract-hash.test.ts`,
the `src/styles/tokens.test.ts` shape: (a) always: the sha256 of each copy's raw bytes equals
the hash pinned in the test — the two §7 lines, copied here verbatim with their paths;
(b) `describe.skipIf` the sibling checkout is absent: the pinned lines equal the
`contract-hash:` lines of `../Fonnus/docs/read-contract.md`, matched with the pipeline's own
`CONTRACT_HASH_LINE` regex copied from `../Fonnus/scripts/check-config.ts:235` — so a contract
that moved on shows up here, not on a screen; (c) always: after stripping comments the way
`withoutComments` there does, each copy's `import` specifiers are a subset of
`{ 'zod', '../domain/speakable.js' }` for the document file and empty for the speakable file.
Re-copying is the only edit: the test's header says so and names the two pipeline paths.

**3. The flat-key labels are the console's own table, held total by a test.**
`RUNTIME_KEY_MAP` (`../Fonnus/app/src/config/runtime.ts:164`) is not under a hash line, so
it is copied as `src/configuration/flat-keys.ts` — one entry per leaf path, a string or, for
`stt.model`, `tts.model`, `tts.params.speed` and `tts.params.pronunciation_dict_id`, a
per-vendor object exactly as the source spells it, with the source line cited. The test
derives every leaf path from the copied schema (rule 4's walk) and asserts the table's key
set equals it both ways: a leaf the pipeline adds fails here, not silently on screen. The
key *names* are ASSUMED stable until the pipeline pins the map under a hash line
(`PLAN.md` §Waiting on `../Fonnus`).

**4. The form is generated by walking the copied schema, never written by hand.**
`src/configuration/document.ts` walks `runtimeConfigSchema` through zod 4's `_zod.def`
(`type` at each node: `object` → `shape`; `optional` → the inner type; `union` with a
discriminator → one branch per `provider` literal; `enum`, `literal`, `string`, `number`,
`boolean`, `array`, `record`) and yields a flat list of **fields**: path, group (the
top-level key: `turn` · `stt` · `llm` · `tts` · `text`), vendor branch when the path lives
under one, flat key from rule 3, and a control kind decided by the leaf's own schema —
`integer` / `number` with bounds read from the schema's `minValue` / `maxValue` / `isInt`
and the `inclusive` flag of its `greater_than` / `less_than` checks; `boolean`; `enum` with
the schema's `options`; `text`; `textarea` for the five `text.*` leaves; `list` (one entry
per line) for the string arrays; `record` (a JSON textarea) for `sounds_like`. The five
control kinds are the console's rendering vocabulary, not pipeline terms. The walk is also
what rule 3's totality test runs.

The form encodes one document: every field is one value control named `<path>`, and
there is no tick. `documentFromForm(entries)` builds the nested plain object from the
leaves whose control carries text (`isSetText`) — a blank or whitespace-only control is
absent, and absent means the boot value applies (contract §3.4), so an unset leaf reads
"boot value", with the value when the last call ran it from boot config — coercing by control kind (a number that does not parse stays the raw
string, so the schema reports the issue on that path; a list is split on newlines and
trimmed; a record is `JSON.parse`d and a parse failure stays the raw string). `stt.provider`
and `tts.provider` are selects with a "boot value" option; the branch leaves under a provider
render only while it is chosen (a client component flips them; with JavaScript off a leaf
every branch shares — `stt.model`, `tts.model`, `tts.params.speed`,
`tts.params.pronunciation_dict_id` — renders once with the union of every branch's options
and no `min` / `max` attribute, the per-vendor bounds in its hint, and the schema refuses the
wrong value at review). Since the pipeline's `313ed5d` (pipeline ADR 0033) the same rule
reads the model too: the four `tts.params` leaves the copy exports as
`ELEVENLABS_DIALOGUE_REFUSED_LEAVES` (`similarity_boost`, `style`, `speaker_boost`,
`speed`) render only while `tts.model` does not satisfy the copy's
`isElevenLabsDialogueModel` — a dialogue model takes `stability` only — so a loaded row
that set one and is switched to `eleven_v4_turbo` shows the leaf as `removed` in the review
diff with "not a setting of eleven_v4_turbo" on the after side, as a vendor swap reads "not
a <vendor> setting" — never "boot value", because the pipeline refuses the merged record
when the box `.env` still sets that knob (pipeline ADR 0033 D5), so no boot value applies;
with JavaScript off nothing hides and the copied schema refuses the leaf at review, on
`tts.params.<leaf>`. `llm.model` is free text,
`stt.model` / `tts.model` are `MODEL_CATALOGUE[provider]`. Each text field offers "restore
shipped text" (fills `SHIPPED_TEXT.<leaf>`); "back to boot config" submits the empty
document. The groups are tabs over the one `<form>` (`?group=`, ADR 0006), so an edit on
one tab is submitted with the others; with JavaScript off every group shows at once. A leaf
whose control differs from the newest row is marked pending, with a rollback to the newest
row's value. The `textarea`, `list` and `record` controls edit in a popover opened from a
two-line preview. The one thing the blank rule cannot write is an empty string: a stored
`llm.fallback_model = ""` ("no fallback") loads as blank, and a save from the form leaves
the leaf out. Beside each field the value the **last answered call actually ran on**: its
`config_snapshot`'s flat key, resolved per vendor from the snapshot's own `STT_PROVIDER` /
`TTS_PROVIDER` first, both spellings of the three renamed Deepgram keys read through
`canonicalKey` / `KEY_ALIASES` of `src/dashboard.ts` (ADR 0009); a key the snapshot lacks
reads "—" (that vendor did not run), never a default.

**5. A save is two steps in one server action: review, then insert.** One server action
(`'use server'`, `src/app/configuration/actions.ts`) dispatches on a hidden `intent` field
and feeds one `useActionState` in the client form. `review`: `documentFromForm` →
`runtimeConfigSchema.safeParse` → issues mapped to fields by `path.join('.')` (a cross-field
`superRefine` reports on its leaf path, so it maps too) → the diff against the **newest row of
the tenant** (boot config, `{}`, when there is no row or the newest row is one the copy refuses
— trap 6), never against the document the form was loaded from, so a restore of a history row
shows what it would change (amended by ADR 0012 D7; the head still says which row the form
was loaded from), in path order, each leaf `added` / `removed` / `changed` → the advice
list: `disclosureAdvice(text.greeting)`, and "`llm.model` changed but `llm.params.reasoning`
is not set in this row" (the runbook §10 rule the schema does not enforce). Issues block the
save; advice never does (rule 6). The review renders the proposed document as JSON, the
diff, the issues, the advice, the note field, and one sentence: *takes effect on the next
call answered; no call in progress changes*. The review, its diff and its hidden `document`
carry the **parsed** document when it parses (the raw one, with its issues, when it does not),
so the row the save inserts is byte for byte what was reviewed — a trimmed `context_text` or
`tts.voice` is reviewed trimmed (amended by ADR 0012 D7). `edit` returns to the form with the document
as submitted. `save`: `requireAccount()` (a throw is rendered as the refusal, nothing
written) → parse the hidden `document` JSON **again** on the server (the client's copy is
never trusted) → `insertRuntimeConfig` → `revalidatePath` and `redirect` to
`/configuration?tenant=<id>&group=<tab>&saved=<new id>` — the same tab, the head marking
the new row current. The review offers Save only when the diff has at least one entry: a
save that changes nothing is not a row worth writing. The
document, the diff and the advice are pure functions in `src/configuration/document.ts`;
the action is a thin dispatcher and the only file that touches `FormData`.

**6. The write module is `src/writes/runtime-config.ts`, the first file under `src/writes/`.**
`insertRuntimeConfig({ tenantId, config, note, by })` runs the contract's statement verbatim
on `getEditorPool()` with `created_by = createdBy(by)` (ADR 0007), returns `{ id, createdAt }`,
and maps the three refusals the contract names to one sentence each by SQLSTATE
(`err instanceof DatabaseError` from `pg`, `err.code`): `42501` "the editor role cannot
insert into runtime_config — the credential in EDITOR_DATABASE_URL is not console_editor,
or its grant was revoked"; `23514` "the document is not a JSON object"; `23503` "tenant
`<id>` does not exist in tenant_config". Any other refusal the server returned becomes "the save
failed; nothing was written"; an error that is not the server's answer (the client-side
`query_timeout` of the pool, a dropped connection) becomes "the save did not complete —
reload and check the history before saving again", because the statement may have
committed after the client stopped waiting. The reason goes to stderr only in both cases
(the `error.tsx` rule: a trace can carry the host). No `UPDATE`, no `DELETE`, no `getPool`: the tree scan of `src/writes.test.ts`
already covers the directory, and its "exactly those two places" assertion is extended by
this one file.

**7. "Latest row not applied" is counted, never inferred, over the calls started after the
row.** One aggregate on the `console` pool: among `call_log` rows of the tenant with
`started_at > <newest row>.created_at`, the total and the number whose
`config_snapshot->'runtime'->>'version'` is distinct from the row's id as text — absent
(boot, or a refused row: pipeline ADR 0020 D7) and older both count. Rendered as a warning
only when the second number is above zero: "N of the M calls since row #id ran on boot
config or an older row. The reason is in the pipeline's log line (`reason: timeout | query |
invalid | provider`) and in `fonnus_runtime_config_fallbacks_total` on `/metrics` — not in
this database." No grace window: the pipeline reads the row before the session exists and
stamps `started_at` after (§Verified facts), so a call started before `created_at` never saw
the row and is not counted; a call whose read straddled the insert can be counted as "not
applied" although it legitimately ran on the previous row, and the copy says so: "a call
that was being answered at that moment ran on the row before". The warning is not shown
while the tenant has no row.

**8. Tenant, empty states and a document the copy refuses.** `tenant_config` is read
(`id`, `clinic_name`, ordered by `id`); with one row the head names it and there is no
picker; with more, a select in the head (a GET form, ADR 0006: `?tenant=<id>`), and the
history (an overlay opened from the head's History button), the warning and the form
are scoped to it. No row yet → every leaf "boot value", the
head reads "boot config — no row yet", history is the empty state. A `{}` row → the same
form, the head names the row. "Load into form" on a history row is a link
(`?from=<row id>`): the form starts from that row's document and the head says which row it
started from; the save is still a new row. A stored document the copied schema refuses
(trap 6: a row written by hand, or a contract that has moved) is never pretended to parse:
history shows it raw with the refusal, the form starts from boot config with a warning that
names both possible causes and points at the drift test.

**9. Editing not configured, no account, and the footer.** `getEditorPool() === undefined`
→ the form renders with a caveat "editing is not configured: EDITOR_DATABASE_URL is unset"
and no submit; `requireAccount()` throwing → the same form, read-only, with "no account came
through the reverse proxy; nothing can be written" — never a placeholder name. The footer of
every screen becomes `console · <account>` / `console · no account` (ADR 0007 D6; the word
"edits" would overstate D1 — two inserts, not editing). The `stt` and `tts` cards carry the
"as of boot at `<booted_at>`, build `<build_sha>`" line of the tenant's newest `boot_report`
row, which is what the vendor and voice selects are drawn from (ADR 0012 D3–D5, rule 4 of
`docs/redesign.md` §4.2 as rewritten); only without a report does the head fall back to the
former fixed caveat — every vendor is offered, this box refuses a vendor it holds no key for,
and `/healthz` `vendors` on the box says which — check it before choosing.

**10. Form controls are new surface, styled by copy.** `src/ui/input.tsx`, `select.tsx`,
`textarea.tsx` take their shell from
`../Fonnus-Web-UI/src/app/ui/Field.module.css` `.control` / `.input` / `.textarea` @ 302e3e8
(the 1px inset ring, `--surface-card`, `--radius-md`, the focus ring on the shell) — the
same source `src/ui/window-control.tsx`'s `FIELD` string already abbreviates, which moves
into the new primitives. Native `<select>` is used, not the Web-UI's drawn listbox: nothing
here needs type-ahead, and a native control works with JavaScript off. The nav glyph is the
Web-UI's `settings` (`icons.ts:113`), copied unchanged as the third sidebar glyph. `src/ui/overlay.tsx` is a native
`popover="auto"` panel (centred, or a right-hand sheet): it opens with `popovertarget` and
no script, and the controls inside it are still submitted with their form.

## Why

- **Generated, never hand-written (rule 1)** because the pipeline's schema moves
  additively and a hand-written form is a second schema that drifts. The walk over
  `_zod.def` is the only way to generate from the bytes as pinned; zod 4 documents `.def`
  as the JSON-serialisable definition meant for exactly this kind of traversal, and the
  `minValue` / `maxValue` / `isInt` getters as the reading of a schema's checks.
- **The alias over the alternatives.** Byte-identity is not negotiable (rule 1 and pipeline
  ADR 0021 D2 pin the hash), so the `.js` specifier stays. Rejected: switching the console to
  `moduleResolution: nodenext` (every relative import in the console would need an
  extension, and Next's own template is `bundler`); a nested `tsconfig.json` under
  `src/contract/` (tried: Turbopack does not read it for this — §Verified facts); building
  with webpack (`next build --webpack`) for one import; a physical `speakable.js` shim (a
  third file the drift test would have to explain). One alias line, keyed on the exact
  string the drift test pins, is the smallest change and its failure mode is a build error.
- **One action with an intent, not two** because the form has one state object: `useActionState`
  binds one action to one state, and the review and the save are two steps of the same
  submission, not two forms. The pure functions keep the split testable without a request.
- **Review before insert, on the server, twice.** The first parse is what the operator sees;
  the second is the trust boundary — the hidden `document` field is client-held between the
  two steps. Postgres' CHECK is the last net, not the first.
- **Counting, not inferring (rule 5).** The reason a row was not applied is in the pipeline's
  log and counter and nowhere in this database; the tab can say how many, never why. The
  `is distinct from` comparison against the id as text is the whole computation, so the
  count needs no per-call read and no cast that a stray value could throw on.
- **Every row in history, no `LIMIT`.** "Current" is the newest, a restore is "load into
  form", and a bounded read would hide the row an operator is looking for. Rows are written
  by hand, one per edit; the size that makes this a problem is the revisit trigger.
- **The flat-key copy is a table, not a hash-pinned file** because the pipeline does not pin
  it yet; the totality test is what turns a silent drift into a failing test, and the name
  drift the test cannot catch is written down as ASSUMED with its settling observation.
- **Trap 6 is rendered, not resolved.** A document the copy refuses is either one the
  pipeline also refused (`reason: invalid`) or the sign of a stale copy; the tab can show
  both possibilities and the drift test can settle one of them — pretending it parses could
  do neither.

## Rejected

- A route handler plus `fetch` for the save (fork 4's alternative): more code for the same
  request, and it loses the no-JavaScript path a server action keeps.
- A one-click restore of the shipped greeting that skips review: rule 2 says the diff comes
  before every save; the banner's button opens the review with the greeting already
  restored, and the save is one more click (a fork in the report).
- Inferring "not applied" from `stt_model` / `tts_model` or from the snapshot's flat keys
  when `runtime` is absent: rule 5 forbids it, and a boot value equal to the row's value
  would make the inference wrong in both directions.
- Reading `runtime_config` for the "ran on" hints: a row is what was asked for, not what
  ran; the snapshot is the only record of the effective value (contract §3.4).

## Revisit when

- **The pipeline pins `RUNTIME_KEY_MAP` under a contract-hash line** (PLAN §Waiting on):
  `src/configuration/flat-keys.ts` becomes a byte copy under rule 2 and the totality test
  becomes a hash check.
- **Turbopack resolves `.js` to `.ts` under `bundler`**, or the pipeline's contract file
  stops importing with an extension: the alias line is deleted and the drift test's import
  pin is what says so.
- **A tenant's history passes a few hundred rows**: history is paged in the URL (ADR 0006),
  the newest row and the warning unchanged.
- **A second tenant is real** (ADR 0002's clinic trigger): the picker exists already; the
  question then is whether an account is scoped to a tenant, which is ADR 0007's revisit.
- **The pipeline exposes the fallback reason per call** (a column, or a `reason` label the
  console can read): rule 5's warning names the reason instead of pointing at the log.

## Verified facts

- Turbopack resolution of `import '../domain/speakable.js'` to `speakable.ts`: **fails**
  under `moduleResolution: bundler` (`Module not found`), fails with a nested
  `src/contract/tsconfig.json` set to `nodenext`, and **succeeds** with
  `turbopack.resolveAlias: { '../domain/speakable.js': './src/contract/domain/speakable.ts' }`
  — observed 2026-09-19 with `next build` on Next.js 16.3.4 in a scratch project using this
  repo's `node_modules`. The gating on `nodenext` is in
  `turbopack/crates/turbopack-resolve/src/typescript.rs` (context7 `/vercel/next.js`). `tsc`
  under `bundler` and vitest 4.1 resolve the same specifier without help (same probe).
- Next.js 16 server actions: a `'use server'` file exports async functions; with
  `useActionState(action, initialState)` the action's signature is `(prevState, formData)`
  and its return value is the next state; `redirect` is called outside `try/catch` after
  the mutation and `revalidatePath` before it (context7 `/vercel/next.js`, forms and
  redirecting guides).
- zod 4: `z.int()` is a number format check (`format: 'safeint'`); `safeParse` returns
  `{ success: false, error }` with `error.issues[]` of `{ code, path: PropertyKey[], message }`;
  a schema's `_zod.def` carries `type` and `checks`; union `.options` / `.def.options`,
  `ZodOptional.unwrap()`, `ZodArray.unwrap()`; `.minValue` / `.maxValue` / `.isInt` /
  `.minLength` / `.maxLength` are getters computed from the checks (zod 4.6 notes; this
  repo will install 4.6.x, the pipeline pins `^4.4.3`) (context7 `/colinhacks/zod`).
- `pg` ^8.23: a query error is a `DatabaseError` (re-exported from `pg-protocol` by `pg`
  and `@types/pg`) with `code` (SQLSTATE), `severity`, `table`, `constraint` (context7
  `/brianc/node-postgres`, the constraint-error integration test).
- The contract hashes: `sha256sum` of the two pipeline files at `../Fonnus` `ddd5624`
  equals the two `contract-hash:` lines of `../Fonnus/docs/read-contract.md` §7
  (2026-09-18), so a byte copy passes rule 2 as it is.
- Read order at call open: `SessionManager.start()` awaits `callConfigFor(uuid)` before
  constructing the `CallSession` (`../Fonnus/app/src/session/session-manager.ts:162`); the
  `call_log` row is written from `callStarted` (`../Fonnus/app/src/persistence/call-sink.ts:119-139`,
  `callLogRow` at `rows.ts:100`) with an instant taken after that — so `started_at` is
  after the read, which is what decision 7 stands on.
- `config_snapshot.runtime` is set whenever a row was read and parsed
  (`../Fonnus/app/src/config/snapshot.ts:65`), and `runtimeConfigSchema.safeParse({})`
  succeeds (every group is optional), so a `{}` row yields `runtime.version` on the next
  call's snapshot; the refused row is the only "absent" path (pipeline ADR 0020 D7).
- The rule "an edit that changes `llm.model` sets `llm.params.reasoning` in the same row" is
  a comment on the leaf and a runbook §10 rule, not a refine
  (`../Fonnus/app/src/config/runtime-document.ts:466-467`): advice, not refusal, here.

## Assumed

- The flat-key names in `RUNTIME_KEY_MAP` are stable — settled when the pipeline pins the
  map under a contract-hash line (PLAN §Waiting on).
- The two copies pass this repo's ESLint spine unchanged (`speakable.ts` carries an
  `eslint-disable-next-line no-control-regex`) — settled by `pnpm lint` in dispatch A; the
  fallback is an `eslint.config.mjs` override scoped to `src/contract/**`, never an edit of
  the bytes.
- `config_snapshot->'runtime'->>'version'` renders the JSON number as the same digits
  `runtime_config.id` renders to as text — settled by the first save on the box (the
  verification list in the plan: the next call's version equals the new id and the warning
  is silent).
